# Technical specification

## Context

The existing .NET 10 scaffold exposes a controller endpoint through Mediary
and registers an empty `UrlShortenerDbContext` with Npgsql. This slice adds the
write-oriented Management API from `Design.md`. It deliberately leaves the
anonymous redirect path and its cache concerns for a separate task.

The existing layer direction remains authoritative:

```text
Domain <- Application <- Infrastructure <- Api
              ^                         /
              +------------------------+
```

Domain owns the short-link state and invariants. Application owns management
use cases and persistence/generation contracts. Infrastructure implements
those contracts with EF Core/PostgreSQL. API owns HTTP, authentication,
configuration binding, and response mapping.

## Proposed solution

### Domain model

Add a `ShortUrl` aggregate with:

- `long Id`, assigned by PostgreSQL when the row is inserted;
- `string ShortCode`;
- `string LongUrl`;
- `string OwnerId`;
- `bool IsDeleted`;
- `DateTimeOffset CreatedAt`;
- `DateTimeOffset UpdatedAt`.

Creation requires non-empty values, leaves `Id` at its unpersisted default,
sets `IsDeleted` to `false`, and starts with equal creation and update
timestamps. Updating a non-deleted resource changes `LongUrl` and `UpdatedAt`
only when the destination actually differs. Deletion sets `IsDeleted` to
`true` and advances `UpdatedAt`; a deleted aggregate cannot be updated or
deleted again through its domain methods.

Do not introduce a status enum or status abstraction. For this slice the only
lifecycle distinction needed by core behavior is whether the resource has
been logically deleted.

Keep setters unavailable outside Domain/EF materialization. Do not add audit
events, a generic entity base type, or a general repository abstraction.

### Application use cases

Add one Mediary command and handler for each operation:

- `CreateShortUrlCommand(ownerId, url)`;
- `UpdateShortUrlCommand(ownerId, shortCode, url)`;
- `DeleteShortUrlCommand(ownerId, shortCode)`.

The create and update handlers return a representation containing
`ShortCode`, `ShortUrl`, and `Url`; delete has no response body. Application
uses focused contracts for short-link persistence, short-code candidate
generation, time, nonce creation, and the configured public URL builder only
where deterministic tests require a seam. Prefer .NET's `TimeProvider` and
`Guid`-based nonce generation over custom framework replacements when they
remain easy to test.

Do not place HTTP status codes or ASP.NET types in Application. Model expected
outcomes with small explicit result types or exceptions that the API maps
consistently:

- validation failure;
- resource not found for the requesting owner;
- short-code attempt exhaustion.

### Persistence

Map `ShortUrl` to a `short_urls` PostgreSQL table. Use snake-case column names
or explicit names consistently. Required storage behavior is:

```text
id          bigint generated by PostgreSQL identity, primary key
short_code  varchar(6), required, unique
long_url    varchar(2048), required
owner_id    bounded varchar, required
is_deleted  boolean, required, default false
created_at  timestamp with time zone, required
updated_at  timestamp with time zone, required
```

Configure `Id` as a database-generated `bigint` identity. The application does
not calculate or allocate identifiers. Map `IsDeleted` directly to the
`is_deleted` boolean; no enum, lookup table, or separate status object is
needed. Name the unique short-code index or constraint so its violation can be
recognized precisely. Do not make `long_url` unique and do not filter the
short-code uniqueness rule by `is_deleted`: deleted codes remain permanently
reserved.

Add the first EF Core migration for this model under Infrastructure and add the
EF design package/configuration needed for repository-local migration commands.
Migrations are applied explicitly; application startup must not silently alter
the schema.

The focused persistence implementation supports:

- inserting a candidate and distinguishing only the named short-code unique
  violation from other database failures;
- loading one active resource by both `shortCode` and `ownerId` for mutation;
- saving an update or logical deletion.

On a recognized candidate collision, detach/clear the failed tracked insert as
needed before retrying. Do not perform a check-then-insert uniqueness query.
Unexpected database errors propagate to the normal server-error path.

### Short-code generation

Use the exact Base62 alphabet:

```text
0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ
```

For each creation, generate one UUID nonce. For collision counter values
starting at zero, form an unambiguous, invariant byte representation of:

```text
ownerId + destination URL + nonce + counter
```

Hash it with SHA-256, reduce the resulting unsigned value modulo `62^6`, and
Base62-encode it as exactly six characters, left-padding with `0` when needed.
Reuse the same nonce and increment only the collision counter between attempts.
Allow five total insertion attempts. If all five candidates collide, return
the attempt-exhausted outcome; do not loop indefinitely.

Generation must be deterministic for fixed inputs so unit tests can prove the
alphabet, length, repeatability, counter sensitivity, and retry sequence. It
does not need to promise cryptographic secrecy or globally uniform distribution.

### Authentication

Add one ASP.NET Core Bearer authentication scheme for Management API
controllers. Bind a runtime configuration collection in which every entry has
an opaque `Token` and an `OwnerId`. Token values are supplied through user
secrets or environment variables and are never committed. Empty or duplicate
tokens and empty owner identifiers are invalid configuration when present;
an empty collection may start the service but authenticates nobody.

For a request with a configured token, create an authenticated principal with
the mapped owner identifier in a dedicated claim. Management actions obtain
`ownerId` only from that claim; request bodies and route values cannot choose
an owner. Missing, malformed, or unknown Bearer credentials produce `401` and
the standard `WWW-Authenticate: Bearer` challenge. Apply authorization to the
Management API controller, not to the anonymous root endpoint.

Use a timing-safe comparison for token values when practical with the bounded
configured token set. Do not log credentials or include them in error bodies.
Token issuance, persistence, hashing at rest, refresh, and rotation are outside
this task.

### Configuration

Add a required, absolute HTTP/HTTPS `PublicBaseUrl` setting. The development
configuration may safely use `http://localhost:8080`; it is not a secret. URL
building trims a trailing slash from the configured base and appends exactly
one slash plus the short code.

The README must explain that this prototype has no user table or registration flow: a "user"
is an arbitrary stable owner identifier associated with an opaque token in
runtime configuration.

Document the runtime shape for the token-owner collection using placeholders,
never working token values. Provide copyable local commands equivalent to:

```bash
export URL_SHORTENER_TOKEN="$(openssl rand -hex 32)"
dotnet user-secrets --project Api set \
  "ManagementAuth:Tokens:0:Token" "$URL_SHORTENER_TOKEN"
dotnet user-secrets --project Api set \
  "ManagementAuth:Tokens:0:OwnerId" "local-user-a"
```

The README must then show migration application, service startup, and an
authenticated request that reads the Bearer value from
`$URL_SHORTENER_TOKEN`, followed by an optional `unset URL_SHORTENER_TOKEN`.
It must explain how to add a second owner by using array index `1`, and how to
list or remove local user-secret entries without printing token values in the
repository. Commands must be run from, or explicitly target,
`src/url-shortener-api`.

Also document the equivalent hierarchical environment-variable names for
non-user-secrets environments, but do not add real credentials or recommend
committing a populated environment file. Keep the existing PostgreSQL
configuration contract.

## Interfaces and behavior

### Create

```http
POST /api/v1/short-urls
Authorization: Bearer <configured-token>
Content-Type: application/json

{"url":"https://example.com/path"}
```

A successful request returns:

```http
HTTP/1.1 201 Created
Location: <configured-public-base-url>/<shortCode>
Content-Type: application/json

{
  "shortCode": "aZ91Kb",
  "shortUrl": "http://localhost:8080/aZ91Kb",
  "url": "https://example.com/path"
}
```

Every call uses a fresh nonce and attempts to insert a new row. No destination
lookup or deduplication occurs. `Location` equals the returned `shortUrl`, even
though redirect resolution is implemented in a later task.

### Update

```http
PUT /api/v1/short-urls/{shortCode}
Authorization: Bearer <configured-token>
Content-Type: application/json

{"url":"https://example.com/new-destination"}
```

For an owned active resource, return `200 OK` with the same representation
shape as create and the unchanged short code. If the URL is already equal to
the accepted request string, perform no database state change and preserve
`UpdatedAt`; this gives repeated identical requests the same final state.

### Delete

```http
DELETE /api/v1/short-urls/{shortCode}
Authorization: Bearer <configured-token>
```

For an owned non-deleted resource, persist `IsDeleted = true` and return `204
No Content` with an empty body. Repeating the delete returns `404`, while the
resulting resource state remains deleted.

### Ownership and concealment

Update and delete query records by `(shortCode, ownerId)` with
`IsDeleted = false`.
Return the same `404 Not Found` Problem Details response when the code is
unknown, deleted, or owned by a different principal. Do not perform a second
query that distinguishes those cases.

## Data and state

Destination validation accepts a JSON string that:

- is present and not empty or whitespace;
- has at most 2,048 characters;
- parses as an absolute URI;
- uses the `http` or `https` scheme;
- contains a non-empty host.

Persist and return the accepted absolute URL string without fetching it,
following redirects, changing case, stripping query/fragment data, or adding a
trailing slash. This avoids unexpected semantic normalization.

Route short codes are valid only when they contain exactly six Base62
characters. An invalid route code receives the same `404` result as an unknown
resource after authentication. JSON binding/type errors and destination
validation errors return `400` using ASP.NET Core Validation Problem Details.

All persisted timestamps use UTC `DateTimeOffset`. Entity IDs use PostgreSQL-
generated `bigint` identity values and are not exposed in the Management API
contract. A successful update or delete is committed before its HTTP success
response is produced.

## Error cases

- Missing, malformed, or unknown token: `401 Unauthorized` with a Bearer
  challenge and no resource lookup.
- Invalid JSON or destination: `400 Bad Request` with Validation Problem
  Details; no persistence call.
- Invalid, unknown, deleted, or differently owned short code on mutation:
  `404 Not Found` with Problem Details.
- Five consecutive named short-code unique conflicts: `503 Service
  Unavailable` with generic Problem Details and no internal values exposed.
- Any other database or unexpected failure: standard `500 Internal Server
  Error` handling; do not reinterpret it as a collision or expose stack traces
  outside Development.

No `409 Conflict` is part of the public contract because candidate collisions
are an internal creation concern handled by retry.

## Test strategy

Bob works in small red-green-refactor slices and retains tests that prove:

1. Domain creation with `IsDeleted = false`, no-op repeated update, changed
   update, logical delete, and invalid transitions after deletion.
2. Destination validation boundaries, including both accepted schemes,
   relative/unsupported/missing-host values, and the 2,048-character limit.
3. Deterministic six-character Base62 generation, alphabet membership,
   padding, counter sensitivity, and the fixed five-attempt collision sequence.
4. Application creation always inserts a new resource, retries recognized
   collisions, stops after five attempts, and uses authenticated ownership for
   mutation lookup.
5. Application update preserves code and is state-idempotent; delete is logical;
   both conceal missing, deleted, and foreign-owned resources as not found.
6. API integration behavior for `401`, `400`, `404`, `201`, `200`, and `204`,
   response bodies, `Location`, Bearer challenge, owner extraction, and the
   continued anonymous `GET /` behavior. Replace external persistence at this
   level with a narrow deterministic test double rather than requiring a live
   database for every API test.
7. EF model metadata and a real PostgreSQL integration/smoke path prove the
   database-generated `bigint` identity, column limits, `is_deleted`
   persistence, migration application, global code uniqueness, and the main
   create/update/ownership/delete flow.
8. README instructions use placeholders, match the implemented configuration
   keys, and can be followed locally without placing a token in tracked files.

Tests must never print configured token values. Avoid EF's in-memory provider
for evidence about relational uniqueness or migrations.

## Validation commands

Run from `src/url-shortener-api` unless stated otherwise. Bob and Fede may add
focused test filters as files are introduced, but final validation includes:

```bash
dotnet restore UrlShortener.sln
dotnet build UrlShortener.sln --no-restore
dotnet test UrlShortener.sln --no-build
dotnet ef migrations list --project Infrastructure --startup-project Api
docker compose -f docker-compose.development.yml config
docker compose -f docker-compose.development.yml up --build --detach
dotnet ef database update --project Infrastructure --startup-project Api
```

Then run authenticated HTTP requests, with secret token values supplied only
through process environment or user secrets, to prove:

1. unauthenticated create is `401`;
2. one owner creates two different codes for the same destination;
3. that owner updates one code;
4. another owner receives `404` when updating or deleting it;
5. the owner deletes it and a repeated delete is `404`;
6. PostgreSQL still contains the logically deleted row and the unique code.

Finally verify the existing anonymous endpoint and tear down without deleting
the named volume:

```bash
curl --fail --show-error http://localhost:8080/
docker compose -f docker-compose.development.yml down
```

The root response remains exactly `Hello World!`. Validation records HTTP
statuses and redacted resource data, never token contents.

## Explicitly deferred

- Public redirects and `302` behavior.
- Redis/cache-aside and mutation-driven invalidation.
- Management reads/listing, pagination, search, and administrative operations.
- Analytics, audit event storage, channels, and workers.
- Rate limiting, reputation checks, blacklists, and abuse reporting.
- Token issuance, a user database, OAuth/OIDC, token rotation, and production
  secret management.
- User-selected codes, configurable code length, distributed ID generation,
  and unbounded collision retries.
- Automatic migration at API startup and production deployment automation.
